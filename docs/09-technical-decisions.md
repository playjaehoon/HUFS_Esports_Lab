# 기술 선택 검토와 변경 이유

검토일: 2026-09-14. 이 문서는 저장소 코드와 공식 문서를 바탕으로 한 **이 실습실 규모에 대한 판단**입니다. 실제 운영 트래픽·서버 설정은 아직 측정하지 않았으므로 성능의 최선이나 처리량을 보장하지 않습니다.

## Flask/Jinja는 유지한다

현재는 학생 가입·좌석 선택·예약 조회와 운영진 관리가 중심입니다. 서버가 HTML을 만드는 Flask/Jinja 구조로 충분히 구현할 수 있으며 PythonAnywhere 연결과 후임자의 학습 범위를 유지할 수 있습니다. React·별도 API 서버로 전면 교체하면 빌드·인증·배포 대상을 늘리므로, 현재 요구만으로 그 비용을 정당화하기 어렵다고 판단했습니다.

앱 초기화는 `application.py`의 `create_app()`으로 분리했습니다. 테스트·개발·운영 설정을 나누고 여러 테스트 앱을 독립적으로 만들 수 있는 Flask 공식 패턴입니다. `app.py`는 기존 WSGI 연결을 유지하는 호환 진입점입니다. [Flask Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/)

현재 요청 처리는 `routes.py`에 모이고 인증·예약·관리 명령은 별도 파일로 나눴습니다. 경로와 팀 규모가 더 커지면 학생/운영진 Blueprint로 분리할 수 있습니다. 지금 모든 함수를 여러 계층으로 쪼개는 것은 후임자가 요청 흐름을 추적하는 비용도 함께 고려해야 합니다.

## 오래되거나 비효율적이던 부분은 바꿨다

| 초기 방식·문제 | 현재 변경 | 이유·한계 |
| --- | --- | --- |
| 로그인 여부만으로 관리자 보호 | 서버 역할 검사와 예약 소유권 검사 | 링크를 숨기는 것만으로 권한을 보장할 수 없음 |
| 짧은 PIN과 원문 저장·표시 | 학생은 숫자 6자리·해시, 관리자 비밀번호는 12~128자 | 기존 원본/백업 PIN의 보호·폐기는 별도 필요 |
| 상태 변경 폼·API의 요청 위조 방어 부족 | Flask-WTF CSRF 전역 적용·POST 로그아웃 | JavaScript 전송도 CSRF 토큰 포함 |
| 프로세스에 의존하는 시도 제한 | DB 기반 계정·접속 경로 제한 | SQLite 쓰기 비용이 생기므로 고부하 시 별도 저장소 검토 |
| 학번 문자열로 예약 소유권 판단 | 변경되지 않는 회원 FK·과거 학번 소유권 유지 | 학번 변경 후 이력 유실·다중 계정 우회 방지 |
| 중복 조회 후 저장 | DB 고유 제약 + 하나의 쓰기 트랜잭션 | 동시 요청에서도 DB가 마지막으로 중복을 거절 |
| 화면 조회 시 자동 노쇼·정지 | 운영진이 종료 후 사유를 입력해 노쇼 확정 | 체크인 누락으로 자동 제재되는 문제 방지 |
| 여러 곳의 시간·최대 이용시간 계산 | `booking.py` 공통 규칙·한국 시간 | 예약 조회와 생성 기준을 일치시킴 |
| 단일 전역 앱·초기화에 의존 | 앱 팩토리·격리 테스트·Alembic | 설정과 DB 변경을 재현·검토 가능 |
| 전체 학생/이력 한꺼번에 표시 | 목록 페이지 분할·필터 | 더 큰 데이터에서 쿼리 수·인덱스 추가 측정 필요 |

CSRF는 일반 폼뿐 아니라 세션을 사용하는 JavaScript 요청에도 적용해야 하므로 `CSRFProtect`와 `X-CSRFToken` 헤더를 사용합니다. [Flask-WTF CSRF 안내](https://flask-wtf.readthedocs.io/en/1.2.x/csrf/)

## SQLAlchemy·스키마 관리

조회는 `db.select()`, `session.scalar()`/`scalars()`, `session.get()`을 사용합니다. SQLAlchemy 2.x 공식 ORM 조회 형태에 맞추었으며 새로운 코드에서 레거시 `Model.query`에 의존하지 않습니다. [SQLAlchemy 2.x SELECT 안내](https://docs.sqlalchemy.org/en/20/orm/queryguide/select.html)

모델의 기존 `db.Column` 선언은 그 자체로 동작하지 않는 방식이 아닙니다. 현재 변경에서는 데이터 안전성과 이관에 집중했고, 타입 힌트 중심의 `Mapped` 전환은 후임 개발 환경과 정적 분석 도입 시 따로 검토할 수 있습니다.

스키마는 Flask-Migrate/Alembic 이력으로 관리합니다. 자동 생성은 후보 변경 파일을 만드는 과정이므로 데이터 변환·이름 변경·제약을 사람이 검토해야 합니다. `create_all()`은 기존 테이블 구조를 바꾸지 않습니다. [Flask-Migrate 안내](https://flask-migrate.readthedocs.io/en/latest/), [Flask-SQLAlchemy 스키마 안내](https://flask-sqlalchemy.palletsprojects.com/en/stable/quickstart/)

초기 DB는 그대로 ALTER하지 않고 읽기 전용 원본에서 새 파일로 가져옵니다. 알 수 없는 스키마·소유자 없는 예약·중복을 조용히 버리지 않고 중단합니다. `0001`은 빈 DB에만 쓰며 운영 스키마가 다르면 별도 이관 검토가 필요합니다.

## SQLite는 조건부로 유지한다

현재 27석 도면과 30분 단위 예약은 하나의 PythonAnywhere 앱·짧은 쓰기 작업에 맞는 작은 시스템입니다. 이 범위에서는 별도 DB 서버 운영을 늘리기 전에 SQLite로 검증하는 것이 합리적이라고 판단했습니다. SQLite 공식 문서도 웹사이트 사용을 설명하면서 많은 동시 writer가 필요한 경우에는 클라이언트/서버 DB를 검토하도록 안내합니다. [SQLite 사용 범위](https://sqlite.org/whentouse.html)

날짜·좌석·시간의 고유 제약과 회원·날짜의 고유 제약을 두고, 예약 검증부터 저장까지 `BEGIN IMMEDIATE`로 묶습니다. SQLite는 동시 writer가 하나이며 잠금 경합 때 busy 오류가 날 수 있습니다. 현재 연결은 최대 15초 잠금 대기 후 오류 응답을 처리합니다. 트랜잭션 안에 외부 HTTP 호출이나 오래 걸리는 작업을 넣지 않습니다. [SQLite 트랜잭션](https://sqlite.org/lang_transaction.html)

다음 상황에서는 PostgreSQL 등 서버 DB로 옮기는 비용을 다시 검토합니다. 이 목록은 측정할 판단 기준이며 현재 그런 문제가 발생했다는 뜻은 아닙니다.

- 예약 시작 시 로그인·예약이 몰려 잠금 오류나 대기 시간이 반복된다.
- 여러 앱 서버가 같은 DB에 써야 하거나 실시간 PC 상태 수집 같은 지속 쓰기가 추가된다.
- 백업·복구·보관량을 현재 운영자가 감당하기 어려워진다.

현재 구현은 SQLite 전용 트랜잭션과 upsert를 사용하며 앱도 다른 DB URL을 거절합니다. `DATABASE_URL`만 PostgreSQL로 바꿔서 전환할 수 있다고 안내하면 안 됩니다. 이관·락 전략·동시성 테스트·배포 구성을 함께 바꿔야 합니다. WAL 설정도 공유 호스팅의 저장소 성격을 확인한 뒤 결정합니다.

## 의존성과 다음 검토

현재 직접 의존성은 `requirements.txt`에 Flask 3.1.3, Werkzeug 3.1.8 등으로 고정했습니다. 개발 테스트 의존성은 `requirements-dev.txt`로 구분했습니다. 버전 번호만 최신으로 바꾸는 것보다 실제 Python·호스팅 환경에서의 설치, 회귀 테스트, 이관 검증이 우선입니다.

간접 의존성까지 재현하는 잠금 파일·업데이트 자동화와 GitHub CI는 후속 작업입니다. 운영 배포 전에는 새 가상환경의 설치 결과를 기록하고 `pip check` 및 테스트로 호환성을 확인합니다. 새로운 라이브러리·호스팅 이전·SPA 전환은 해결할 구체적 문제, 도입 비용, 후임자가 운영할 수 있는지를 함께 기록한 뒤 결정합니다.
