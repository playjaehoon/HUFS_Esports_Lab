1. `git status`와 [진행표](07-progress.md)를 읽어 중단된 작업과 다른 사람의 변경을 확인합니다.
2. 새 작업이면 `codex/<작업명>` 브랜치를 만듭니다. 이미 진행 중인 브랜치에서는 계속 작업합니다.
3. 한 가지 목적의 코드·회귀 테스트·해당 문서를 함께 수정합니다.
4. `.\.venv\Scripts\python.exe -m pytest -q`로 관련 기능을 검증합니다. 화면 변경은 데스크톱·모바일에서도 확인합니다.

7. 진행표와 CHANGELOG에 완료·미완료·검증·배포 여부를 남깁니다. push·PR·운영 배포는 각각 별도로 기록합니다.

예를 들어 내 예약 기능 수정이라면 코드만 먼저 커밋하지 말고 소유권·취소 테스트와 사용법까지 하나의 검토 단위로 묶습니다. 문구만 바꾼 경우에는 구현을 그대로 복제하는 테스트를 추가하지 않습니다.

## 테스트와 데이터 관리

현재 `tests/`는 `create_app()`과 임시 DB·가상 학생을 사용합니다. 역할 경계, CSRF, 예약 소유권, 입력 검증, 동시 예약, 상태 전이, 정보 변경과 세션 무효화를 검증합니다. 최종 확인 범위와 결과는 [진행표](07-progress.md)에 기록합니다.

예약과 차단 시간은 DB에 자정부터의 분(`start_minute`, `end_minute`)으로 저장합니다. 예약 당시 직접 접속 주소는 `booking_ip`에 저장하며 관리자 화면에서만 확인합니다. 예약 카드의 IP 삭제 버튼은 제거했지만 기존 관리자 전용 삭제 경로는 유지합니다. IP를 자동 삭제하지 않으며 백업본에도 남을 수 있으므로 기관의 보관·폐기 기준과 별도 정리 절차를 확정해야 합니다. 운영에 올릴 때에는 DB를 먼저 백업하고 같은 DB에 `flask db upgrade`를 실행해 `0003` 시간 변환과 `0004` IP 필드 추가를 완료한 뒤 웹 앱을 Reload합니다.

`tools/audit_snapshot.py`와 `test_logic.py`는 초기 구현 확인용 자료입니다. 현재 배포 전 회귀 테스트로 실행하지 않습니다. 초기 JSON을 보존해 문제의 배경을 이해하고, 새 동작은 `pytest`로 검증합니다.

모델을 바꾸면 Alembic 변경 파일을 만들고 생성된 SQL·제약·데이터 변환을 직접 검토합니다. `create_all()`은 기존 테이블 변경을 처리하지 않습니다. `0001`은 빈 DB 전용이며 기존 초기 DB에는 [별도 파일 이관](05-deployment.md)을 사용합니다. DB·실제 회원정보·환경 파일·백업·가상환경·생성 ZIP은 Git에서 제외합니다.

학번·이름을 바꿔도 예약과 제한은 변경되지 않는 내부 회원 ID에 연결합니다. 사용했던 학번은 같은 회원에게 계속 귀속하므로 다른 계정의 재가입에 사용할 수 없습니다. 학번 오입력·타인 선점 분쟁은 학생증을 대조하는 운영진 절차가 필요하며 자동 계정 복구 기능은 아직 없습니다.
