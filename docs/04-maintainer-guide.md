# 개발·인수인계 가이드

## 역할별로 시작하기

현장 담당자는 공지·예약 운영·방문 확인 절차를, 개발 담당자는 소스·로컬 실행·테스트를, 배포 담당자는 서버 설정·DB 백업·복구를 맡습니다. 한 사람이 여러 역할을 맡아도 계정과 책임자는 기록합니다.

## 어디를 수정하는가

| 바꾸려는 것 | 현재 위치 | 함께 확인할 것 |
| --- | --- | --- |
| 공지·예약 열기/닫기·최대 시간 | 관리자 대시보드 → 시스템 설정 | 운영 사이트에서 저장하면 즉시 영향 |
| 회원가입·로그인 문구 | `templates/student_register.html`, `student_login.html` | 실제 승인 정책은 `app.py`에도 있음 |
| 공통 메뉴·실습실명 | `templates/layout.html` | 학생/관리자/비로그인 상태 모두 확인 |
| 예약 폼·이용수칙 | `templates/index.html` | 시간·제한을 JS·서버와 일치시킬 것 |
| 좌석 배치·조회·예약 전송 | `static/js/main.js` | 실제 좌석, CSS 배치, 서버 검증 |
| 색·여백·모바일 | `static/css/style.css` | 템플릿 인라인 스타일이 덮어쓸 수 있음 |
| 로고·글꼴 | `static/images/`, `static/fonts/` | `convert.py`의 옛 절대 경로는 그대로 실행하지 않음 |
| 인증·권한·예약 규칙 | `app.py` | 서버 테스트, 사용자별 접근 권한 |
| 저장 항목 | `models.py` | 운영 DB 마이그레이션 필수 |
| 신규 로컬 DB 초기화 | `init_db.py` | 운영 업데이트용이 아님. 공개 기본 관리자 생성 주의 |

현행 관리자 화면의 권한·PIN 문제를 수정하기 전에는 접근 계정 확대를 보류합니다. 장기적으로 비개발 담당자가 바꿔야 하는 운영시간·휴실·공지·좌석 고장은 관리 화면으로 옮깁니다.

## 로컬 개발 순서

1. [README](../README.md)의 명령으로 새 복제본과 가상환경을 만듭니다. 현재 로컬 재현은 Python 3.11.7에서 확인했습니다. 서버 Python 버전과의 호환성은 배포 전에 따로 확인합니다.
2. `git status`로 기존 작업을 확인하고 작업 브랜치를 만듭니다.
3. 작은 범위의 변경을 하고 학생·운영진 화면과 관련 기능을 점검합니다.
4. 차이를 읽고 비밀정보·DB·가상환경이 섞이지 않았는지 확인한 뒤 커밋합니다.
5. GitHub에 작업 브랜치를 올리고 PR로 변경 이유·검증을 공유합니다. 검토된 변경을 병합한 뒤 별도 배포 절차를 수행합니다.

예시 명령은 새 기능 작업 기준입니다.

```powershell
git switch main
git pull --ff-only
git switch -c codex/my-reservations
# 파일 수정과 검증 후, 수정한 파일만 지정
git diff
git add app.py templates/layout.html
git commit -m "Add student reservation history"
git push -u origin codex/my-reservations
```

`git add`의 파일 목록과 커밋 메시지는 실제 변경에 맞춥니다. GitHub에 push했다고 PythonAnywhere가 자동 갱신되는지는 별개입니다. 현재 저장소에는 자동 배포 설정이 없습니다.

## 검증 도구의 의미

`tools/audit_snapshot.py`는 초기 문제의 관찰용입니다. 임시 폴더의 복사본·가상 데이터만 쓰며 운영 URL을 받는 옵션이 없습니다. 정상 동작을 assert하는 배포 전 테스트로 간주하지 마세요. 앱 구조가 바뀌면 이 도구가 더 이상 맞지 않을 수 있으므로 초기 결과 JSON을 보존하고 새로운 회귀 테스트를 만듭니다.

`test_logic.py`는 고정 날짜와 기존 계정에 의존하는 수동 스크립트입니다. 현재 `requirements.txt`만 설치하면 `requests`가 없어 실행되지 않습니다. 이를 CI로 바로 사용하는 대신, [기능 완료 기준](02-product-spec.md)의 행동을 Flask 테스트 클라이언트와 임시 DB에서 자동 검증하도록 교체합니다.

핵심 회귀 테스트는 역할 경계, 타인 예약 접근, 예약 시간·좌석 검증, 동시 중복 방지, 취소, 정보 수정 후 소유권 유지, 정지·노쇼, 기존 DB 이관입니다. 색·문구만 바꿨을 때는 불필요한 구현 복제 테스트 대신 화면 검수를 합니다.

## 권장 코드 정리 순서

전체 프레임워크 교체보다 현재 Flask 구조 안에서 책임을 나눕니다. `create_app`으로 테스트·개발·운영 설정을 구분하고, 학생 인증·예약·관리 라우트, 공통 권한 검사, 예약 규칙, 설정 읽기를 분리합니다. DB 변경 이력을 도입한 후 새 기능을 올립니다. SQLite 유지 여부는 좌석 중복 방지와 실제 동시 이용 시험으로 판단합니다.

`.env`, `.env.*`(공유용 예시 제외), `.venv/`, 로그·백업 경로는 `.gitignore`에 추가할 개선 항목입니다. **현재 앱은 환경변수를 읽도록 구현되어 있지 않으므로 `.env` 파일만 만들면 설정이 바뀐다고 생각하면 안 됩니다.** 이 진단 작업에서는 실행 설정을 바꾸지 않았습니다.

패키지 고정은 현재 네 개 직접 의존성에만 적용되어 있습니다. 지원 버전·보안 업데이트를 확인한 뒤 간접 의존성을 포함한 재현 가능한 잠금 방식을 마련합니다. 업데이트는 테스트 환경에서 먼저 검증합니다.

## Antigravity 작업 복구와 후임자 연습

기존 PC의 프로젝트 폴더와 PythonAnywhere 소스 디렉터리를 별도 복사본으로 보존하고 GitHub 기준과 비교합니다. `.git` 이력, 미커밋 파일, 이미지 원본, 서버 설정을 확인합니다. 기존 폴더를 새 clone으로 덮어쓰거나 서버에서 무작정 `git reset --hard`하지 않습니다. 대화 기록이 없어도 README·기능 명세·PR 이력을 통해 의도를 남길 수 있습니다.

인수인계 완료 기준은 후임자가 도움 없이 새 PC에서 실행하고, 가상 학생으로 가입·예약·내 예약 조회·취소·현장 확인을 연습하며, 공지 또는 문구 수정 PR을 만들고, 시험 환경 배포와 DB 복구를 수행하는 것입니다. 현재 미구현 기능은 구현 후 이 연습에 포함합니다.
