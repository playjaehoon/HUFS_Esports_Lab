# Git 작업·커밋 규칙

## 언제 커밋하는가

**하나의 목적이 완료되고 관련 검증을 통과했을 때 커밋합니다.** 날짜나 작업 시간보다 변경 목적을 기준으로 합니다.

1. 기능 수정과 해당 회귀 테스트·사용법을 한 커밋으로 묶습니다.
2. 서로 다른 작업으로 넘어가기 전, 검증된 현재 작업을 커밋합니다.
3. 작업을 마칠 때는 통과한 작업을 커밋하고 진행표를 갱신합니다. 미완료 작업을 완료로 기록하지 않습니다.
4. DB 구조가 달라지면 이관 스크립트·이관 테스트·배포 순서를 같은 변경에 포함합니다.
5. 문서·인수인계 자료만 바꾸는 작업은 별도 `docs` 커밋으로 남깁니다.

## 브랜치·검토·배포

- `main`: 검토를 마친 기준 코드. 새 작업은 `codex/<작업명>` 브랜치에서 시작합니다.
- 커밋: 로컬의 복구 가능한 작업 이력입니다.
- push: GitHub에 브랜치를 공유하는 단계입니다. 커밋과 별개입니다.
- PR·병합: 변경 이유·검증·데이터 영향을 검토하고 main에 반영합니다.
- 배포: 백업·서버 설정·이관·Reload·점검을 수행하는 별도 단계입니다. 커밋이나 push가 배포 완료를 뜻하지 않습니다.
- 공유된 커밋은 force push로 지우기보다 새 수정 커밋으로 고칩니다. 운영 서버에서 편집한 변경도 먼저 보존합니다.

## 커밋 전 확인

`git status`, `git diff`, 관련 테스트, `git diff --check`를 확인합니다. `git add`는 의도한 파일을 지정하고 staged diff도 읽습니다. DB·학생 데이터·비밀번호·키·환경 파일·백업·가상환경·생성 ZIP은 커밋하지 않습니다. 공개용 설정 예시에는 실제 값을 넣지 않습니다.

메시지 형식은 `유형(영역): 변경 결과`입니다.

```text
fix(auth): restrict administrative routes and protect session requests
feat(student): add reservation history and account editing
docs(handover): update progress and package operating guides
```

유형은 `fix`, `feat`, `docs`, `test`, `refactor`, `chore`를 사용합니다. 실패하는 테스트를 숨기거나 변경과 무관한 파일을 같은 커밋에 묶지 않습니다.

현재 단계와 미완료 사항은 [진행표](07-progress.md), 배포 여부는 그 문서의 배포 상태를 기준으로 확인합니다.
